# 架构资料索引与维护规则

本目录回答"系统现在是什么样、为什么这样、怎么演进"，与 [`docs/changes/`](../changes/README.md) 的单次改动材料分开维护。

## 资料

| 文件 | 内容 | 维护者 |
| --- | --- | --- |
| [`current-runtime.md`](./current-runtime.md) | 当前模块图、请求时序、宿主与 Service 边界、Session / JSONL 等已实现事实 | 开发者随实现更新，架构师审阅 |
| [`product-charter.md`](./product-charter.md) | 产品是什么、模块边界、技术克制与文档分层 | 产品设计师 / 架构师，长期原则 |
| [`decisions/`](./decisions/) | 长期影响较大的取舍（ADR） | 架构师提案，用户确认后 `accepted` |
| [`evolution.md`](./evolution.md) | 重要结构变化的"之前 → 之后"、原因、关联需求/ADR/PR | 开发者或架构师在合入时更新 |

## 维护规则

1. **当前架构只写已实现的事实。** 目标状态写在 `docs/changes/<id>/spec.md`，不要提前写进 `current-runtime.md`。
2. **Spec 与当前架构分开。** Spec 说明本次相对现状的变化；合入后再回写当前架构。
3. **ADR 用于长期影响较大的取舍**：消息/记录建模、模块边界、宿主通信、兼容迁移等。记录背景、备选方案、选择理由、代价与状态，不为每个小改动创建 ADR。
4. **演进记录按重要结构变化记录**：之前 → 之后、原因、关联需求、ADR、PR 和合入提交；区分已落地、已接受未实现、仍在提议。
5. **实现 PR 携带对应架构更新**，与代码一起审查、合入；没有结构变化时在 PR 描述写理由。
6. **每份架构基线标记对应提交。** 并行任务合入前核对最新 `origin/develop`，避免不同分支用各自版本覆盖整体架构。
7. 不依靠"让某个 Agent 记住所有事情"维护架构；维护职责落在每次任务和 PR 上。
8. **教程、历史计划和旧决策草稿不进产品仓库。** 它们放仓库外备份；需要在仓库里留痕时，写进 `evolution.md` 的演进记录，而不是混进当前架构。
9. **单次改动的 PRD / Spec / Plan / Verification 跟代码一起入库、一起 review。** 仓库是公开的，敏感材料另用私有存储。

## ADR 状态

| 状态 | 含义 |
| --- | --- |
| `proposed` | 已提出，等待用户/维护者确认，不能当作已定方案 |
| `accepted` | 用户确认采用，但可能尚未实现 |
| `implemented` | 已落地，代码与文档一致 |
| `superseded` | 被后续 ADR 取代，保留历史并链接新 ADR |
| `rejected` | 评估后不采用，记录原因避免重复讨论 |

## 并行与合并

- 每个任务记录所基于的 `origin/develop` 提交。
- 合入前先同步最新 `origin/develop`，处理文档与代码的共同影响。
- 架构文档冲突时，以"当前整体架构"为准，不按分支各自覆盖。
